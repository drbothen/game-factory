## Section 6: CAP-006 — Contract-Driven Simulation Quality Verification (P0)

### 6.1 Overview

CAP-006 is the machine-verifiable quality spine for game-factory. It replaces
vsdd-factory's software behavioral contracts with a game-domain quality model
comprising three contract layers and one enforcement gate:

1. **Simulation Behavioral Contracts (sim-BCs)** — machine-checkable assertions
   over serialized simulation state: economy invariants, damage I/O matrices,
   FSM state legality, and AI behavior-tree outputs.

2. **Design Intent Contracts** — the machine-verifiable subset of design intent:
   reachability, solvability, balance bands, conservation invariants, no-softlock
   detection. Non-machine-verifiable claims are explicitly delegated to the
   Playtest Protocol (CAP-008). The delegation is a formal declaration in the
   contract, not a gap.

3. **Replay-Regression Contract Linkage** — Each sim-BC is linked to at least one
   replay-regression contract (CAP-003). The simulation contract defines *what*
   correctness means; the replay contract verifies that correctness is preserved
   across code changes.

4. **TDD Red Gate Enforcement** — The pure-sim slice (all code under test by a
   sim-BC) operates under opt-in strict TDD Red Gate (reused from vsdd-factory
   verbatim per extraction-boundary-validated.md §3.1). Failing tests must exist
   before any implementation. Degrades gracefully to off for engine-bound/render code.

### 6.2 Boundary: Machine-Verifiable vs Playtest-Delegated

The critical design principle of CAP-006 is the explicit two-part split:

| Type | Verifiable | Mechanism |
|------|-----------|-----------|
| Economy invariants (conservation, balance bands, sink/faucet) | YES | Sim-BC + property-based test |
| Damage I/O (input damage → output HP delta) | YES | Sim-BC + unit test |
| FSM legality (no illegal state transitions) | YES | Sim-BC + model checking |
| AI behavior-tree output (given state → expected action) | YES | Sim-BC + headless runner |
| Reachability (all game areas/states reachable) | YES | Graph traversal |
| Solvability (game has at least one valid path to completion) | YES | SAT/graph + property test |
| Balance bands (win-rate within declared ε) | YES | Simulation + statistical check |
| No-softlock (no unreachable progress states) | YES | State-space exploration |
| Conservation (resources conserved across transactions) | YES | Invariant assertion |
| "Fun" / "Feel" / "Polish" / "Challenge curve" | NO | Playtest Protocol (CAP-008) |
| Narrative emotional impact | NO | Playtest Protocol (CAP-008) |
| Art style appropriateness | NO | Playtest Protocol (CAP-008) |

## Section 7: CAP-007 — 11-Dimension Convergence Tracking (P0)

### 7.1 Overview

CAP-007 is the release-gating spine of game-factory. It adapts vsdd-factory's
convergence-loop engine (novelty-decay, 3-clean-streak, ADAPT per
extraction-boundary-validated.md §3.2) to the game domain by redefining the
11 convergence dimensions.

**Release rule:** All required dimensions must reach GREEN or be explicitly
DEGRADED to a declared fallback before release. No dimension may be BLOCKED
(i.e. failed without an explicit declared fallback) at release.

The convergence loop runs:
1. Evaluate all 11 dimensions.
2. Any dimension not GREEN triggers a convergence iteration.
3. An adversarial review pass runs each iteration (fresh context, information asymmetry).
4. Three consecutive clean evaluations (no findings, all dims GREEN or declared-degraded)
   = convergence reached.
5. Novelty-decay: repeated non-novel findings in an adversarial pass do not reset the
   3-clean-streak counter.
