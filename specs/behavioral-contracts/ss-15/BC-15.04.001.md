# BC-15.04.001: Leaderboards — Server-Authoritative Submit, Tampered Score Rejection, Variants, and Pagination

## Description

The online-services adapter must support server-authoritative leaderboard score
submission and paginated query. Score submission via `online.leaderboard.submit` is
NEVER client-authoritative: the server computes or validates the submitted score against
the player's authoritative game-state record before accepting it. A tampered or
implausible score (one that exceeds what the server's own game-state records as
achievable) MUST be rejected with `E-OSVC-003` (`ScoreRejectedByServer`). Query via
`online.leaderboard.query` supports board variants (`daily`, `weekly`, `all-time`) and
cursor-based pagination.

**Server-authority enforcement for leaderboards is specified here as an operational
contract between the online-services adapter and the BaaS backend. The foundational
server-authority invariant (no-trust-client, CWE-602) is governed by D-SEC dimension
BC-7.11.002 and BC-7.11.003. This BC cites those contracts and asserts that violations
in the leaderboard path surface through the D-SEC dimension — this BC does NOT duplicate
the server-authority spine.**

## Preconditions

1. The online-services adapter manifest is valid (BC-15.01.001 passed).
2. `capabilities.leaderboards.serverAuthoritative` is `true` (enforced by BC-15.01.001).
3. `capabilities.leaderboards.fidelity` is `full` or `partial`.
4. A valid session token has been obtained (BC-15.02.001 passed).
5. The `boardId` is a leaderboard configured in the BaaS backend.

## Postconditions

1. **PASS — legitimate submit:** `online.leaderboard.submit` with
   `{playerId, boardId, score, metadata?}` where score is within the server's acceptable
   range for the player's game-state returns `{rank: <int>, score: <number>}`.
2. **FAIL — tampered score rejected:** Score exceeds what the server's game-state records
   as achievable for this player (e.g., score = MAX_INT when player has only completed
   tutorial). Error: `E-OSVC-003` (`ScoreRejectedByServer`). Message:
   `leaderboard.submit: score <score> for board '<boardId>' rejected — exceeds server-computed
   maximum for playerId '<playerId>'`.
3. **PASS — query with variant:** `online.leaderboard.query` with
   `{boardId, variant: "daily"|"weekly"|"all-time", limit: <n>, cursor?}` returns
   `{entries: [{rank, playerId, score}], nextCursor?}`. `entries` length ≤ `limit`.
4. **PASS — cursor pagination:** When `nextCursor` is returned, a subsequent query with that
   cursor value returns the next page without duplicating or skipping entries.
5. **PASS — variant not supported:** If the manifest's `variantsSupported` does not include
   the requested variant, the adapter returns `E-EAP-002` (`CapabilityUnsupported`) for that
   variant, not a generic error.
6. **PASS — max/replace idempotency (retry safety):** V1 leaderboard boards are strictly
   **max/replace-style**: the server retains only the player's personal best score for each
   `(playerId, boardId)` combination. A resubmission of the same score or a lower score is a
   **no-op** — `{rank, score}` is returned unchanged and no entry is double-counted. A
   resubmission of a higher score **replaces** the stored value and returns the updated rank.
   This makes `online.leaderboard.submit` naturally idempotent under client retry after a
   network timeout: a repeated identical call produces the same observable state as a single
   call. No client-supplied dedup key is required for v1.
7. **FAIL — backend unreachable:** Error: `E-OSVC-001` (`BackendUnreachable`).

## Invariants

1. Score submission is always server-validated. The adapter may never accept a score by
   trusting only the client payload. (Governed by BC-7.11.002; violations surface via D-SEC.)
2. The leaderboard query result is deterministic for a given cursor position: repeating the
   same query with the same cursor returns the same entries (within eventual consistency window).
3. Board variants are an adapter-declared capability, not a runtime parameter. Requesting an
   undeclared variant returns CapabilityUnsupported, not an empty list.
4. **V1 boards are max/replace only.** For any `(playerId, boardId)`, the backend stores at most
   one score — the player's all-time personal best. Cumulative (additive) boards are explicitly
   out of scope for v1 and require a new BC + dedup-key protocol before introduction.

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | Submit score = 0 (valid minimum) | PASS: rank and score returned |
| EC-002 | Submit score > server-computed maximum | FAIL: E-OSVC-003 ScoreRejectedByServer |
| EC-003 | Query with variant not in manifest's `variantsSupported` | E-EAP-002 CapabilityUnsupported |
| EC-004 | Query with `cursor` from a previous page | PASS: next page returned without duplicates |
| EC-005 | `leaderboards.fidelity: none` | E-EAP-002 CapabilityUnsupported on all leaderboard methods |
| EC-006 | Modified client sends arbitrary score (e.g., 9999999999) via direct JSON-RPC | E-OSVC-003; server checks against authoritative game-state |
| EC-007 | `limit: 0` in query | Adapter returns empty `entries: []` without error |
| EC-008 | Client retries `online.leaderboard.submit` after network timeout (same score, same player, same board) | PASS: max/replace board treats identical resubmission as no-op; `{rank, score}` unchanged; no double-count |
