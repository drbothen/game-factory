# BC-15.03.001: Cloud Save — Write/Read Round-Trip and Conflict Resolution

## Description

The online-services adapter must support per-player cloud save persistence via
`online.save.write` and `online.save.read`. A write followed by a read for the same
`(playerId, saveKey)` must return the data that was written (round-trip correctness). The
adapter's manifest declares its `conflictResolution` strategy
(`last-write-wins | server-authoritative | client-authoritative`). When a save conflict
occurs (concurrent writes with mismatched versions), the adapter applies the declared
strategy. An unresolvable conflict returns `E-OSVC-005` (`SaveConflictUnresolvable`).

## Preconditions

1. The online-services adapter manifest is valid (BC-15.01.001 passed).
2. `capabilities.cloud_save.fidelity` is `full` or `partial` (not `none`).
3. A valid session token has been obtained (BC-15.02.001 passed).
4. The backend (e.g., Nakama) is reachable.

## Postconditions

1. **PASS — write:** `online.save.write` with `{playerId, saveKey, data, version?}` returns
   `{version: "<string>", timestamp: "<ISO-8601>"}`. `version` is a monotonically increasing
   opaque string usable for optimistic concurrency checks on subsequent writes.
2. **PASS — round-trip:** `online.save.read` with `{playerId, saveKey}` after a successful
   write returns `{data: <same-data>, version: "<same-version>", timestamp: "<ISO-8601>"}`.
   The `data` field is byte-for-byte identical to the data in the write call.
3. **FAIL — conflict (version mismatch):** Two concurrent writes for the same `(playerId, saveKey)`
   with different version tokens. The adapter applies its declared `conflictResolution` strategy:
   - `last-write-wins`: the later write wins; the earlier write is silently overwritten. No error.
   - `server-authoritative`: the server picks the authoritative version and returns it; the
     losing write receives `E-OSVC-005` with `{winner_version, winner_data}` in the error payload.
   - `client-authoritative`: the adapter returns the conflicting versions to the caller; the
     caller must resolve and re-submit. Error: `E-OSVC-005` with both versions in payload.
4. **FAIL — backend unreachable:** Error: `E-OSVC-001` (`BackendUnreachable`).
5. **FAIL — session expired during write:** Error: `E-OSVC-002` (`SessionExpired`).
6. **PASS — read miss:** `online.save.read` for a `saveKey` that has never been written
   returns `{data: null, version: null, timestamp: null}`. This is NOT an error — missing
   save is a legitimate first-session state.

## Invariants

1. `version` returned on write must be used on the next write for that `saveKey` to enable
   conflict detection. A write with no `version` field bypasses conflict detection (first write).
2. The `conflictResolution` strategy is declared at manifest time and cannot be changed per-call.
3. `data` is opaque bytes from the factory's perspective — the adapter does not inspect or
   transform save data contents.

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | Write with no `version` (first write for key) | PASS: version assigned; returned in response |
| EC-002 | Read for saveKey that was never written | `{data: null, version: null, timestamp: null}` — not an error |
| EC-003 | Concurrent writes with same version token; `last-write-wins` | One write wins; no error surfaced to either writer |
| EC-004 | Concurrent writes with same version token; `server-authoritative` | Loser gets E-OSVC-005 with winner data; winner gets normal response |
| EC-005 | `cloud_save.fidelity: none` | E-EAP-002 CapabilityUnsupported on all save calls |
| EC-006 | Very large save data (>1MB) | Adapter returns E-OSVC-005 with message `save data exceeds backend size limit` if backend rejects |
