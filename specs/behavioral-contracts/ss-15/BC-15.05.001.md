# BC-15.05.001: Matchmaking — Lobby Lifecycle (Create and Join)

## Description

The online-services adapter must support lobby-based matchmaking via
`online.matchmaking.createLobby` and `online.matchmaking.joinLobby`. A host player
creates a lobby and receives a `{lobbyId, joinCode}`. Other players join via the
`joinCode`. The adapter reports capacity limits from its manifest
(`matchmaking.lobbyMaxPlayers`). Lobbies that exceed capacity reject new join requests
with `E-OSVC-014` (`LobbyCapacityExceeded`). Progress on matchmaking waits is reported
via `$/progress` notifications.

## Preconditions

1. The online-services adapter manifest is valid (BC-15.01.001 passed).
2. `capabilities.matchmaking.fidelity` is `full` or `partial`.
3. A valid session token has been obtained (BC-15.02.001 passed).
4. The BaaS backend supports lobby creation (e.g., Nakama match API).

## Postconditions

1. **PASS — create lobby:** `online.matchmaking.createLobby` with `{hostPlayerId, config}`
   returns `{lobbyId: "<uuid>", joinCode: "<string>"}`. Both fields are non-empty strings.
   `lobbyId` is unique per backend instance.
2. **PASS — join lobby:** `online.matchmaking.joinLobby` with `{playerId, joinCode}`
   returns `{lobbyId: "<uuid>", players: [{playerId, joinedAt}]}`. The joining player
   appears in `players`. Player count ≤ `matchmaking.lobbyMaxPlayers`.
3. **FAIL — lobby capacity exceeded:** `joinLobby` when lobby is at `lobbyMaxPlayers`
   capacity. Error: `E-OSVC-014` (`LobbyCapacityExceeded`).
4. **FAIL — invalid join code:** `joinCode` does not resolve to an active lobby. Error:
   `E-OSVC-015` (`LobbyNotFound`).
5. **PROGRESS — matchmaking wait:** While waiting for enough players to fill a lobby, the
   adapter emits `$/progress` notifications with `{token, kind: "matchmaking-wait",
   playersNeeded: <n>, elapsedMs: <n>}` at reasonable intervals (≤ 5 seconds).
6. **FAIL — backend unreachable:** Error: `E-OSVC-001` (`BackendUnreachable`).

## Invariants

1. `lobbyId` is assigned by the backend, not by the client. The factory core does not
   generate or predict lobby IDs.
2. `joinCode` is short-lived: it expires if unused within the adapter's declared TTL.
   An expired join code returns `E-OSVC-015`.
3. `lobbyMaxPlayers` is a hard cap. The adapter must enforce this cap server-side, not
   client-side only.

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | Host creates lobby; host is counted as a player | `players` list includes host; count = 1 after create |
| EC-002 | Join with expired join code | E-OSVC-015 LobbyNotFound |
| EC-003 | Join when lobby is at max capacity | E-OSVC-014 LobbyCapacityExceeded |
| EC-004 | `matchmaking.fidelity: none` | E-EAP-002 CapabilityUnsupported on all matchmaking methods |
| EC-005 | `$/progress` not received within 10s during wait | Adapter implementation quality issue; VP-TBD-310 covers this timing bound |
| EC-006 | `lobbyMaxPlayers: 0` in manifest (adapter default) | Implementation must document the adapter-default value; not treated as unlimited |
