# BC-14.01.003: Comfort Certify Is Always Human-Gated (Fail-Closed for XR Comfort)

## Description

The `comfort_certify` capability in any XR adapter manifest must always be declared with
`fidelity: human-gated`. The factory may never autonomously certify XR comfort, declare a
comfort rating, or suppress the headset-playtest gate. Comfort / simulator-sickness /
presence requires a physical headset and a human vestibular system to evaluate — it is
physiologically impossible to assess headless. This is not a policy choice but a physical
boundary, analogous to and stronger than the GPU/playtest boundary. Any manifest that
declares `comfort_certify` at a fidelity level other than `human-gated` is a factory
defect (DI-006).

## Preconditions

1. An XR adapter manifest is being created or updated.
2. The `comfort_certify` capability is being declared.

## Postconditions

1. If `comfort_certify` is declared with `fidelity: human-gated`: the manifest is valid
   for this field; a human-gated task is recorded in the pipeline's task list with:
   - What must be done: "Conduct XR headset playtest; validate comfort/nausea/presence
     for all declared locomotion modes; assign shipping comfort rating."
   - Responsible role: cert-owner or XR QA lead.
   - Required artifacts: xr-comfort-spec (BC-14.02.002), headset playtest session report.
   - Success criterion: human sign-off on the shipping comfort rating.
2. If `comfort_certify` is declared with any fidelity value other than `human-gated`:
   schema validation fails with `E-XR-001`; the manifest is rejected; no XR adapter
   registration proceeds.
3. The human-gated task appears in the convergence report under the `cert-preflight +
   distribution-readiness` dimension and the `human-gated` sub-dimension.

## Invariants

1. `comfort_certify: human-gated` is the only valid configuration for this capability.
   This invariant is enforced at schema validation time, not at runtime.
2. Suppressing the human-gated comfort-certify task is a hook-detectable defect (DI-006).
3. The factory may derive a *candidate* comfort rating heuristically from the
   xr-comfort-spec (e.g., "smooth locomotion + no vignette → likely Moderate or higher")
   but this candidate rating is explicitly labeled `heuristic_estimate` in the artifact
   and must never be presented as the shipping rating without human sign-off.
4. An automated comfort score or nausea prediction produced by any agent without a human
   headset test is a factory defect identical in class to an automated fun-score (DI-007
   extension to XR).

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | `comfort_certify: {fidelity: full}` — developer attempting to claim automated comfort cert | `E-XR-001` at schema validation; manifest rejected; message explains physiological requirement |
| EC-002 | `comfort_certify: {fidelity: none}` — developer claiming comfort cert is not applicable | `E-XR-001`; comfort_certify must be human-gated for all XR adapter manifests (cannot be none) |
| EC-003 | `comfort_certify` capability omitted entirely from manifest | `E-XR-001` (required field); separately enforced by BC-14.01.001 schema |
| EC-004 | Pipeline agent attempts to auto-sign off the comfort-certify task without human evidence | Hook-detected as defect per DI-006; task remains open; convergence report blocked |
| EC-005 | `deferred: true` manifest (seam-only, no runtime) — comfort_certify task still emitted? | Yes: task is emitted with `status: deferred` and a note that it activates when implementation is added; not blocking in deferred mode |
