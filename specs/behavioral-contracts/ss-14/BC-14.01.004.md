# BC-14.01.004: XR Seam Isolation — Zero Core Changes on XR Adapter Add/Remove

## Description

Adding, removing, or replacing an XR adapter must produce zero changes to factory core
layers 1-2 (the orchestration spine and the game methodology layer). The XR seam is
strictly a Layer-4 adapter: all XR knowledge is quarantined in the XR adapter manifest
and its associated driver. The factory core must never contain XR-specific imports,
capability names, or runtime-detection logic. This is the XR extension of DI-001 (factory
core never names a specific engine) applied to XR platforms. It is verifiable as a
source-level diff: adding a new XR adapter should produce changes only in Layer-4 adapter
files plus the seam registry — zero changes in core.

## Preconditions

1. A baseline game spec build exists with no XR adapter registered (or with an existing
   XR adapter).
2. An XR adapter manifest is being added (or the existing adapter is being removed).
3. The factory pipeline has Layer-1 and Layer-2 module boundaries clearly defined.

## Postconditions

1. After adding an XR adapter:
   - All changes are confined to Layer-4 adapter files plus the seam registry.
   - Diff of Layer-1 and Layer-2 source files: empty (zero lines changed).
   - Core artifacts (game design specs, balance data, narrative, audio manifests, code)
     are bitwise identical to the no-XR build.
2. After removing an XR adapter:
   - Same isolation guarantee: Layer-1 and Layer-2 unchanged.
   - XR-specific artifacts are absent from the output tree.
   - All non-XR artifacts are bitwise identical.
3. The conformance result for this property is recorded as `core_isolation: pass` in the
   XR adapter's conformance status.

## Invariants

1. The factory core (Layers 1-2) may never import an XR SDK, reference an XR platform by
   name, or contain XR capability-detection logic. All such references are Layer-4 only
   (DI-001 extended to XR).
2. The XR seam registry is the only permitted point of extension — new XR adapters are
   registered in the seam registry, not wired into core.
3. This isolation property is verifiable without running any XR hardware: a source diff
   on a reference game spec before and after XR adapter addition must show zero core changes.
4. The isolation property applies equally to the visionOS adapter and any future
   non-OpenXR XR targets.

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | Developer accidentally adds an XR SDK import to a core Layer-1 file | Pre-commit hook or CI check detects the import; build is rejected with `E-XR-003` (core isolation violation) |
| EC-002 | XR adapter added to a game spec that previously had no XR; diff check run | Layer-1/2 diff: empty; Layer-4 diff: new XR adapter files only |
| EC-003 | XR adapter removed from a game spec that had one; diff check run | Layer-1/2 diff: empty; XR artifacts absent from output; non-XR artifacts bitwise identical |
| EC-004 | Two different XR adapters (e.g., OpenXR on Unity, visionOS on a future target) registered simultaneously | Both are Layer-4 only; core unchanged; seam registry has two entries |
