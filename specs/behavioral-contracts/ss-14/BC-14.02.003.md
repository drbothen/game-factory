# BC-14.02.003: Apple Vision Pro as Separate Non-OpenXR Adapter Target

## Description

Apple Vision Pro (visionOS) uses SwiftUI / RealityKit / ARKit / Metal — it does not
implement the OpenXR loader/runtime architecture and is NOT conformant to OpenXR CTS.
A visionOS XR adapter must declare `backend: visionos` and may not reference any OpenXR
capability IDs, extension namespaces, or CTS conformance fields. Applying OpenXR capability
IDs to a visionOS adapter is a category error: the namespace does not map. This BC
enforces the schema-level isolation between the OpenXR seam (BC-14.01.001–14.01.004) and
the visionOS adapter path. Both are Layer-4 adapters; neither references the other in
core (DI-001). Implementation of both is deferred; this BC concerns seam contract schema.

## Preconditions

1. An XR adapter manifest with `backend: visionos` is being created or validated.
2. The XR seam schema registry is available.

## Postconditions

1. **Valid visionOS manifest:** schema validates `backend: visionos`; the manifest proceeds.
   - `openxr_version` field: absent (not declared).
   - `conformance.suite` field: absent (CTS is an OpenXR concept; visionOS uses App Review
     and Apple's TestFlight + first-party review process).
   - `conformance.status`: may optionally use `apple_review_status` (enum: `pending |
     submitted | approved | rejected`) as a visionOS-specific conformance analog.
   - Capability declarations are from the visionOS capability namespace (see table below),
     NOT from OpenXR extension namespaces.
2. **visionOS manifest with OpenXR fields:** any of the following produce `E-XR-007`
   (OpenXR field used in visionOS manifest):
   - `openxr_version` present.
   - `conformance.suite: khronos-cts` present.
   - Any capability using `XR_KHR_*`, `XR_EXT_*`, or vendor `XR_*_*` namespace IDs.
3. The validated visionOS manifest is stored as a separate entry in the adapter registry
   from any OpenXR adapter.

## visionOS Capability Namespace (non-OpenXR)

visionOS capabilities are named from Apple's native framework stack:

| Capability ID | Framework | Notes |
|--------------|-----------|-------|
| `arkit_world_tracking` | ARKit | World tracking and environmental understanding |
| `realitykit_scene` | RealityKit | 3D scene graph and rendering |
| `realitykit_anchor` | RealityKit | Anchor placement |
| `swiftui_volume` | SwiftUI | Volumetric window presentation mode |
| `swiftui_immersive_space` | SwiftUI | Full immersive space mode |
| `passthrough_compositor` | visionOS | Apple Immersive Spaces compositor |
| `eye_tracking_visionos` | visionOS | On-device eye tracking (system-managed; developer gets focus feedback, not raw gaze) |
| `hand_tracking_visionos` | ARKit | Hand skeleton tracking |
| `comfort_certify` | (all) | Always `human-gated`; same as OpenXR (BC-14.01.003) |

Apple developer eye-tracking note: on visionOS, raw gaze coordinates are not exposed
to apps (system-managed privacy). The `eye_tracking_visionos` capability gives UI focus
feedback only. This differs from OpenXR's `XR_EXT_eye_gaze_interaction`.

## Invariants

1. `backend: visionos` manifests must not contain `openxr_version`. The OpenXR version
   field is undefined and meaningless for visionOS.
2. `backend: visionos` manifests must not use `conformance.suite: khronos-cts`. Apple
   visionOS is not an OpenXR conformant product and cannot be evaluated against CTS.
3. `backend: visionos` manifests must not declare capability IDs from OpenXR extension
   namespaces (`XR_KHR_*`, `XR_EXT_*`, `XR_FB_*`, etc.). Using OpenXR namespace IDs on a
   non-OpenXR platform is a semantic error.
4. `comfort_certify: human-gated` applies equally to visionOS — the requirement is
   physiological, not platform-specific (BC-14.01.003).
5. Adding a visionOS adapter produces zero core changes (BC-14.01.004 applies to all
   Layer-4 adapters, OpenXR and non-OpenXR alike).
6. The visionOS adapter and any OpenXR adapter may coexist in the same game spec (e.g.,
   a game that targets both Vision Pro and SteamVR); they are independent registry entries.

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | `backend: visionos` with `openxr_version: "1.1"` | `E-XR-007`: visionOS manifest must not declare openxr_version |
| EC-002 | `backend: visionos` with `conformance: {suite: khronos-cts, status: pending}` | `E-XR-007`: visionOS does not use CTS; use apple_review_status instead |
| EC-003 | `backend: visionos` with capability `hand_tracking: {fidelity: partial, ext: XR_EXT_hand_tracking}` | `E-XR-007`: XR_EXT namespace may not be used in visionOS manifest; use `hand_tracking_visionos` |
| EC-004 | visionOS manifest with `comfort_certify: {fidelity: full}` | `E-XR-001` (same as OpenXR case; comfort_certify=human-gated is platform-agnostic) |
| EC-005 | visionOS adapter added alongside existing OpenXR adapter | Both valid; two separate registry entries; core unchanged (BC-14.01.004) |
| EC-006 | `eye_tracking_visionos` declared with note that raw gaze is not exposed | Valid; description field may note Apple privacy model; no constraint violation |
| EC-007 | `backend: visionos` with `apple_review_status: approved` | Valid; visionOS-specific conformance field accepted |
