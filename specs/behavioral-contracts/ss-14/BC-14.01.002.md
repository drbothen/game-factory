# BC-14.01.002: OpenXR Capability Fidelity Grading

## Description

Each capability declared in an `xr-adapter` manifest must map to a valid fidelity level,
and that fidelity level must be consistent with the OpenXR extension namespace that
provides the capability. The fidelity grading mirrors the engine adapter's
`full`/`partial`/`none` model, extended with `vendor` for vendor-locked extensions and
`human-gated` for capabilities that require a human in a headset. The OpenXR extension
namespace (`XR_KHR_*`, `XR_EXT_*`, vendor namespaces) is the deterministic source of
truth for which fidelity grade is appropriate.

## Preconditions

1. The XR adapter manifest has passed schema validation (BC-14.01.001).
2. `backend: openxr` is declared (fidelity grading for `visionos` is defined separately
   in BC-14.02.003).

## Postconditions

1. Each declared capability's fidelity level is validated against the fidelity grade
   mapping table.
2. Any fidelity-namespace mismatch produces `E-XR-002` (invalid fidelity grade for
   capability).
3. The validated fidelity manifest is recorded as the runtime capability contract for
   the XR adapter.

## OpenXR Extension Namespace to Fidelity Grade Mapping

| Extension class | Allowed fidelity grades | Examples |
|----------------|------------------------|---------|
| OpenXR core (no extension required) | `full`, `none` | Stereo render, basic pose, session lifecycle |
| `XR_KHR_*` (Khronos-ratified) | `full`, `partial`, `none` | `XR_KHR_vulkan_enable2`, `XR_KHR_composition_layer_depth` |
| `XR_EXT_*` (multi-vendor) | `partial`, `none` | `XR_EXT_hand_tracking`, `XR_EXT_eye_gaze_interaction` |
| Vendor: `XR_FB_*`, `XR_META_*` | `vendor`, `none` | `XR_FB_passthrough`, `XR_META_foveation_eye_tracked` |
| Vendor: `XR_MSFT_*`, `XR_HTC_*`, `XR_PICO_*` | `vendor`, `none` | `XR_MSFT_spatial_anchor`, `XR_HTC_hand_interaction` |
| Comfort / human-judgment capabilities | `human-gated` only | `comfort_certify` |

## Invariants

1. A capability backed by a `XR_EXT_*` extension may not declare `full` — it must be
   `partial` or `none` (multi-vendor extensions are not guaranteed across all runtimes).
2. A capability backed by a vendor extension (`XR_FB_*`, etc.) must be `vendor` or `none`.
3. `comfort_certify` always maps to `human-gated` regardless of any extension state.
4. `full` is only permitted for OpenXR core capabilities and `XR_KHR_*` ratified extensions.
5. A capability declared `full` must be supported on ALL conformant OpenXR 1.1 runtimes
   (this is enforced declaratively; actual runtime verification happens at conformance time).

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | Capability `hand_tracking` (backed by `XR_EXT_hand_tracking`) declared `full` | `E-XR-002`: `XR_EXT_*` extensions must be `partial` or `none` |
| EC-002 | Capability `passthrough` (backed by `XR_FB_passthrough`) declared `partial` | `E-XR-002`: vendor-namespace extensions must be `vendor` or `none` |
| EC-003 | `stereo_render` (OpenXR core) declared `full` | Valid; `full` is correct for core capabilities |
| EC-004 | New extension `XR_FUTUREVEND_*` declared (unknown vendor namespace) | Treated as `vendor` class; must be `vendor` or `none` |
| EC-005 | `comfort_certify` declared with any fidelity value other than `human-gated` | `E-XR-001` (schema-level enforcement per BC-14.01.001) prevents this from reaching fidelity grading |
