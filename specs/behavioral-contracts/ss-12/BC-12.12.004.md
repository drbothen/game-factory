# BC-12.12.004: Timeline — Event Ordering and Per-Entity Validity Window Consistency

## Description

> **Timeline store authority (OBS-20-B):** CAP-012 Canon-KB (this BC) is the **authoritative
> timeline store** for all game production. BC-5.04.002 (CAP-005) models the same timeline
> as a consumer/integrity-check view — it verifies consistency of existing timeline data
> but does not own or manage it. Timeline mutations go through this BC; CAP-005 reads for
> validation.

The timeline subsystem maintains an ordered sequence of canon events (organized by era
and ordinal) with per-entity validity windows. A validity window declares the span of
story-time during which an entity exists/is active. The factory machine-checks that
no entity is referenced in generated content before its introduction event or after
its departure event (chronological-reference-integrity).

## Preconditions

1. The `canon-kb` for the target `game_id` is initialized.
2. A timeline-event registration request includes: `era`, `ordinal` (integer; must be
   unique within the era), `summary`, `participating_entity_ids` (list of entity IDs
   present at this event).
3. All entity IDs in `participating_entity_ids` must exist in the entity-registry.

## Postconditions

1. A timeline event is created with:
   - `event_id`: stable unique ID
   - `era`, `ordinal`: unique ordering key within the era
   - `summary`, `participating_entity_ids` as provided
   - `canon_tier`, `provenance`
2. For each entity ID in `participating_entity_ids`, the factory updates the entity's
   `introduced_event_id` to this event if the entity's `introduced_event_id` is currently
   null (first appearance auto-detection).
3. The global ordinal ordering of events within each era is enforced as a strict sequence;
   inserting an event between existing events shifts subsequent ordinals automatically
   (insertion semantics, not append-only).
4. The timeline event is immediately queryable by `event_id`, `era`, and `ordinal`.

## Invariants

1. **Timeline consistency invariant** (machine-checkable, CI gate): for any entity E,
   all generated content referencing E must fall within [introduced_event_id.ordinal,
   departed_event_id.ordinal] (inclusive if departed). References before introduction
   or after departure are `CHRONOLOGICAL_REFERENCE_VIOLATION` — a continuity defect.
2. Ordinals within an era are unique (unless both events are explicitly `concurrent: true`)
   and form a contiguous sequence starting from 1. Gaps are not permitted; ordinal insertion
   updates subsequent events. Concurrent events sharing an ordinal are only valid when both
   carry `concurrent: true` — a unilateral `concurrent: true` on only one event is still
   rejected as a collision and treated as an insertion (EC-002). (OBS-20-A fix: reconciles
   this invariant with EC-005 which permits shared ordinals for concurrent:true events.)
3. No event may be assigned `ordinal: 0` or a negative ordinal.
4. The `ambiguity_flag` on a timeline event allows it to exist at multiple apparent
   points in the timeline (for unreliable-narrator or contested-history stories);
   ambiguity-flagged events are excluded from strict chronological-reference-violation
   checks.

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | Event registered with `participating_entity_ids` containing an entity that doesn't exist | Rejected: E-KB-003 (`ENTITY_NOT_FOUND`) with `error.data.unresolved_ids: [...]` |
| EC-002 | Event registered with an `ordinal` that already exists in the era (and the new event is not `concurrent: true` with the existing one) | Factory inserts at the requested ordinal and shifts all subsequent events up by 1; returns E-KB-016 (`ORDINAL_INSERTION_PERFORMED`) with the new ordering |
| EC-003 | Entity referenced in generated content before its `introduced_event_id` | E-KB-015 (`CHRONOLOGICAL_REFERENCE_VIOLATION`) defect emitted; the generative artifact is flagged; loremaster is notified |
| EC-004 | Entity's `departed_event_id` is set to an event that precedes `introduced_event_id` | Rejected: E-KB-017 (`INVALID_ENTITY_VALIDITY_WINDOW`) |
| EC-005 | Two events in the same era at the same ordinal (concurrent events) | Concurrent events may share an `ordinal` only if both are explicitly marked `concurrent: true`; otherwise, the second registration is treated as an insertion (EC-002) |
| EC-006 | An era with no events is queried | Returns an empty list with `status: empty`; not an error |

| `departed_event_id` set to ordinal 2 when `introduced_event_id` is ordinal 5 | E-KB-017 (`INVALID_ENTITY_VALIDITY_WINDOW`) | error (EC-004) |

## Verification Properties

| VP | Property | Proof Method |
|----|----------|-------------|
| VP-1 | For all entities with `introduced_event_id` and `departed_event_id` set, `introduced.ordinal <= departed.ordinal` (non-negative validity window) | Property-based test over all entity pairs in the registry |
| VP-2 | Ordinals within each era form a contiguous integer sequence from 1 | CI check: for each era, sort events by ordinal; assert sequence is [1, 2, 3, ...] with no gaps |
| VP-3 | No generated artifact may reference an entity at a story-time before the entity's `introduced_event_id` ordinal (continuity check is a CI gate) | Integration test: generate artifact referencing entity before introduction; assert `CHRONOLOGICAL_REFERENCE_VIOLATION` emitted |
