# BC-12.12.008: Retcon Propagation — Where-Used Impact Analysis

## Description

When a hard-canon fact is superseded by a retcon (BC-12.12.006), the factory
automatically identifies all previously accepted narrative artifacts that referenced
or asserted the now-superseded fact (where-used analysis). The factory produces a
`retcon-impact-list` and emits a human-gate task to the loremaster to review and
re-check each affected artifact. The factory does NOT automatically update the
affected artifacts — human review is required for each.

## Preconditions

1. A retcon operation has been completed via BC-12.12.006: a `retcon-record` exists
   linking `superseded_fact_id → new_fact_id`.
2. The affected `game_id`'s artifact store is accessible for traversal.
3. The factory's artifact index tracks which facts each accepted artifact referenced or
   relied upon at continuity-check time (provenance log from BC-12.12.007).

## Postconditions

1. A `retcon-impact-list` is produced containing:
   - `retcon_id`: reference to the `retcon-record`
   - `superseded_fact`: summary of the superseded assertion
   - `new_fact`: summary of the new assertion
   - `affected_artifacts`: list of artifact references, each with:
     - `artifact_ref`: path to the affected artifact
     - `artifact_type`: the type (codex, bark, quest, item-description, etc.)
     - `status`: `needs-review` | `cleared` | `superseded` (initial state is always `needs-review`)
     - `referenced_fact_context`: the text excerpt that relied on the superseded fact
2. A human-gate task is emitted to the loremaster listing all affected artifacts and
   requiring review for each.
3. All affected artifacts transition from `status: continuity-cleared` to
   `status: retcon-pending` in the artifact store — they may not be used in production
   builds until cleared.
4. The loremaster may mark each artifact as `cleared` (the content is still valid
   under the new canon), `needs-update` (requires revision), or `superseded` (the
   artifact itself is no longer valid and must be regenerated).

## Invariants

1. The factory MUST NOT silently accept affected artifacts as valid after a retcon.
   Once a retcon is recorded, the `retcon-pending` status is mandatory for all
   identified affected artifacts until each is individually reviewed (DI-006 analog for
   the narrative domain).
2. The `where-used` analysis must traverse the full artifact store — no artifact type
   is exempt from retcon impact analysis.
3. The loremaster (human) — not any agent — must mark each artifact's review status.
   Auto-clearing all artifacts on retcon is a defect.
4. The `retcon-impact-list` is itself an immutable record: it documents what was
   affected at retcon time. Subsequent changes to affected artifacts create new entries
   on the list but do not modify the original record.

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | Retcon of a `soft` fact that has no affected artifacts (the fact was never referenced) | `retcon-impact-list` created with `affected_artifacts: []`; no human-gate task emitted (nothing to review); the retcon completes without loremaster involvement |
| EC-002 | A cascade retcon: the new fact introduced by a retcon itself conflicts with another existing hard-canon fact | The cascade conflict is detected immediately on `new_fact` registration (BC-12.12.006 check); the loremaster must resolve the cascade before the original retcon is completed |
| EC-003 | Affected artifact is a `human-gated` production artifact (e.g. cinematic script signed off by `cinematic-director`) | The artifact is marked `retcon-pending` AND a separate human-gate task is emitted to the `cinematic-director` in addition to the loremaster, since the cinematic's creative sign-off may need re-doing |
| EC-004 | Loremaster attempts to bulk-clear all affected artifacts without individual review | Factory requires individual `cleared` confirmations per artifact; batch-clear without individual confirmation is rejected |

## Canonical Test Vectors

| Input | Expected Output | Category |
|-------|----------------|----------|
| Retcon of `kael.status: alive → dead`; 3 codex entries and 1 bark referenced "Kael lives" | `retcon-impact-list` with 4 `affected_artifacts`; all 4 transition to `retcon-pending`; loremaster human-gate task emitted | happy-path |
| Retcon of a soft-canon fact with no artifacts referencing it | `retcon-impact-list` with `affected_artifacts: []`; no human-gate task; retcon completes silently | edge-case (EC-001) |
| Loremaster batch-clears all 4 artifacts in one operation | Rejected: individual confirmation required per artifact | error (EC-004) |

## Verification Properties

| VP | Property | Proof Method |
|----|----------|-------------|
| VP-1 | After any retcon, all artifacts in `affected_artifacts` list have `status: retcon-pending` — no affected artifact remains `continuity-cleared` | Integration test: trigger retcon with known affected artifacts; assert all are `retcon-pending` |
| VP-2 | No artifact transitions from `retcon-pending` to `continuity-cleared` without a loremaster action (agent bulk-clear is impossible) | Authorization test: attempt agent-driven transition from `retcon-pending`; assert rejected |
