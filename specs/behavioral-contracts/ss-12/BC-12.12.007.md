# BC-12.12.007: Canon-Continuity-Check Battery (CI Gate)

## Description

The canon-continuity-check battery is a CI-grade battery of machine-checkable assertions
over the Canon-KB and all generated narrative artifacts. It runs automatically when a
new narrative artifact (quest, codex entry, item description, bark, audio log) is
submitted to the factory. The battery checks seven structural invariants and produces
an evidence-grounded defect report. Loremaster adjudication is required for any flag
that involves subjective judgment; structural flags are hard-blocking.

## Preconditions

1. The `canon-kb` for the target `game_id` is initialized and has a non-empty
   entity-registry.
2. A generated narrative artifact has been submitted to the factory for continuity
   validation (the artifact is in `status: pending-continuity-check`).
3. The artifact contains or references extractable entity names, timeline references,
   and fact assertions.

## Postconditions

1. The battery runs all seven checks (see Invariants) against the submitted artifact.
2. A `continuity-check-report` is produced containing, for each check:
   - `check_id` (from the declared check list)
   - `status`: `pass` | `flag` | `blocked`
   - `evidence`: specific text excerpt and KB location that motivated the finding
     (ConStory-Checker pattern — every flag is evidence-grounded, not a black-box score)
   - `resolution_path`: `auto-blocked` (structural violation; artifact rejected) |
     `loremaster-required` (judgment call; artifact held pending human review)
3. If any check returns `blocked`, the artifact is NOT accepted into the artifact store;
   it remains in `status: continuity-blocked` until the defect is resolved.
4. If all checks pass, the artifact transitions to `status: continuity-cleared`.
5. `ambiguity_flag: true` entities and facts are excluded from the contradiction check
   (check 6) but remain subject to all other checks.

## Invariants

The seven mandatory continuity checks are:

1. **Entity-reference integrity**: every proper noun / named entity in the artifact
   resolves to an `entity_id` in the entity-registry. Unresolvable names flag as
   `DANGLING_ENTITY_REFERENCE` (blocked).

2. **Naming-collision detection**: all generated names (new character/location/item
   names introduced in the artifact) pass the naming-registry check before use.
   Collisions flag as `NAMING_COLLISION` (blocked).

3. **Naming-registry rule conformance**: all newly introduced names conform to
   phonotactic rules for their declared cultural context (if rules exist).
   Violations flag as `PHONOTACTIC_VIOLATION` (loremaster-required).

4. **Timeline consistency**: all timeline references in the artifact are chronologically
   valid — entities are not referenced before `introduced_event_id` or after
   `departed_event_id`. Violations flag as `CHRONOLOGICAL_REFERENCE_VIOLATION`
   (blocked).

5. **Broken cross-reference detection**: all KB entity/fact/event IDs explicitly
   cited in the artifact resolve to existing KB entries. Dangling ID refs flag as
   `BROKEN_CROSS_REFERENCE` (blocked).

6. **Canon-fact contradiction**: any hard-canon assertion in the artifact that conflicts
   with an existing `hard` tier canon-fact on the same subject/predicate/window is
   flagged as `CANON_FACT_CONTRADICTION` (loremaster-required; not auto-blocked because
   the new assertion may be intentional retcon pending loremaster approval).

7. **Terminology consistency**: key world-specific terms and canonical spellings in the
   artifact match those in the naming-registry's `canonical_spellings` dictionary.
   Spelling drift flags as `TERMINOLOGY_DRIFT` (loremaster-required).

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | Artifact references only common-language words (no entity names or KB references) | All checks pass vacuously; report notes `no_entity_references_detected: true` |
| EC-002 | Artifact contains an entity name that is ambiguously a collision (the name is similar but not identical to a registry entry) | Check 1 passes (exact match required for blocking); check 7 flags `TERMINOLOGY_DRIFT` if the spelling is in `canonical_spellings` |
| EC-003 | Artifact intentionally references a retired entity as a historical reference (e.g. "the ruins of ancient Kael's citadel") | Passes check 1 (retired entities are still resolvable); no violation |
| EC-004 | Check 6 flags a canon-fact contradiction but the submitting agent claims it is an intended retcon | Artifact remains `continuity-blocked` until loremaster approves the retcon via BC-12.12.006's retcon mechanism; the agent cannot self-authorize a retcon |
| EC-005 | Battery is run on a very large artifact (>10,000 words) | All seven checks complete within the declared timeout (see NFR); partial results are not emitted — the battery must complete fully before reporting |

## Canonical Test Vectors

| Input | Expected Output | Category |
|-------|----------------|----------|
| Codex entry referencing "Kael" (registered) and "Iron Guild" (registered), no timeline violations | All 7 checks pass; artifact → `status: continuity-cleared` | happy-path |
| Codex entry referencing "Zarek" (not in registry) | Check 1 blocks: `DANGLING_ENTITY_REFERENCE {unresolved: "Zarek"}`; artifact → `continuity-blocked` | error (check 1) |
| Bark dialogue: "Kael leads the charge" before `kael.introduced_event_id.ordinal` | Check 4 blocks: `CHRONOLOGICAL_REFERENCE_VIOLATION {entity: "kael", ref_ordinal: 3, introduced_ordinal: 7}` | error (check 4) |
| Item description uses "Grey Guild" when canonical spelling is "Gray Guild" | Check 7 flags: `TERMINOLOGY_DRIFT {found: "Grey Guild", canonical: "Gray Guild"}` (loremaster-required) | flag (loremaster) |

## Verification Properties

| VP | Property | Proof Method |
|----|----------|-------------|
| VP-1 | An artifact with a `DANGLING_ENTITY_REFERENCE` finding is never accepted into the artifact store (blocked status is enforced) | Integration test: submit artifact with unregistered entity name; assert write rejected |
| VP-2 | Every flag in the `continuity-check-report` has a non-empty `evidence` field (evidence-grounded — no black-box flags) | Property-based test over all check types: generate findings and assert `evidence` field is always populated |
| VP-3 | `ambiguity_flag: true` entities are exempt from check 6 (canon-fact contradiction) | Unit test: assert that contradiction check skips facts and entities with `ambiguity_flag: true` |
