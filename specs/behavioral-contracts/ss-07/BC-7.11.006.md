# BC-7.11.006: Server-Authority Invariant — Interest Management (Anti-Wallhack)

## Description

For competitive multiplayer games, the server must not broadcast to a client the
authoritative positions, health, and state of entities that the client's player
character cannot legitimately observe (i.e., they are not in the player's line-of-sight
or field-of-interest). Sending this information creates a wallhack vulnerability:
a modified client can consume the server's broadcast state to display hidden entities.
This invariant requires server-side interest management: the server only sends an
entity's state to a client when that entity is in the receiving player's "area of
interest" as computed server-side.

This BC applies to competitive multiplayer only (where information advantage creates
unfair gameplay).

## Preconditions

1. Game declares `game_mode: competitive_multiplayer` in its profile.
2. `server-authority-spec.interest_management` is declared with the strategy:
   `{distance_based, pvs_based, explicit_aoi_list}`.
3. Entity state broadcasts are generated by the server's update loop.

## Postconditions

1. **PASS:** For every entity state broadcast, the server has evaluated the receiving
   client's area-of-interest and suppressed hidden entities' state updates from the
   broadcast. Hidden entities send no state until they enter the client's AOI.
2. **FAIL:** Server broadcasts entity state (position, health, or any strategic
   game-state variable) for entities not in the receiving client's area-of-interest.
   Error: `E-CONV-006` `CWE-602: wallhack path — entity '<id>' state sent to client
   '<client_id>' outside declared AOI`.
3. **NON-COMPETITIVE EXEMPTION:** Game mode is not competitive multiplayer (co-op,
   MMO with declared enemy visibility, etc.). Invariant INAPPLICABLE unless otherwise
   declared in spec. Note: co-op games may choose to apply AOI as a bandwidth
   optimization; this is voluntary.

## Invariants

1. AOI computation is server-side and runs before each broadcast tick.
2. Entity positions (most critical for wallhack) must always be AOI-filtered for
   competitive multiplayer.
3. "Distance-based" AOI must use server-authoritative positions, not client-reported positions.

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | Player A is behind a wall 50m from Player B; server sends B's position to A | FAIL: E-CONV-006 wallhack path |
| EC-002 | Player A enters the same room as Player B; server adds B to A's AOI | PASS: AOI now includes B; B's state broadcast to A |
| EC-003 | Co-op game sends all ally positions to all players | PASS: co-op is not competitive; invariant inapplicable unless declared otherwise |
| EC-004 | Spectator mode: spectator sees all entity positions | Permitted: spectator clients have a special AOI that is explicitly declared as "all entities"; this is an intentional design choice and must be declared in spec |

## Canonical Test Vectors

| Input | Expected Output | Category |
|-------|----------------|----------|
| Competitive game; enemy behind wall outside AOI | Enemy position NOT in broadcast to player | happy-path |
| Competitive game; enemy enters line-of-sight | Enemy position added to broadcast | happy-path |
| Competitive game; enemy behind wall; state included in broadcast | FAIL: E-CONV-006 wallhack path | error |
