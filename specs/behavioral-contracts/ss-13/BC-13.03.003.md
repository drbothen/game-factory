# BC-13.03.003: Mod Load Determinism — Topological Ordering and Conflict Detection

## Description

When the modding lane is active and one or more mods are loaded, the mod loader must
produce a deterministic, topologically-sorted load order from a given set of mods and
their declared dependency graphs. The same set of mods always loads in the same order,
producing the same resolved virtual filesystem state. Dependency cycles are detected and
rejected; conflicting asset overrides are reported. This extends the factory's existing
replay-regression spine: data-only mods are inherently deterministic, so mod load order
is a subset of the simulation determinism invariants.

## Preconditions

1. The modding lane is active (`modding_enabled: true`) in the validated genre profile.
2. Each mod has a `manifest.json` declaring: `id`, `version` (SemVer), `dependencies`
   (list of `{mod_id, version_constraint}` pairs), `files` (list of overridden asset/data
   paths).
3. All mod manifests have passed UGC schema validation (BC-13.03.002) for their data files.

## Postconditions

1. The mod loader computes a topological sort of the mod dependency graph and produces a
   load order list: `[mod_id_1, mod_id_2, ..., mod_id_N]` where all dependencies of
   `mod_id_k` appear before it.
2. The same input set (same mods, same versions, same dependency declarations) always
   produces the same load order list (determinism).
3. If the dependency graph contains a cycle, loading is rejected with `E-MOD-006`
   (circular dependency detected); no mods are loaded.
4. If two mods both override the same asset/data path, a conflict is reported with
   `E-MOD-007` (file conflict), listing the conflicting mods and the overridden path.
5. The resolved virtual filesystem state — the final set of asset/data overrides after
   applying all mods in load order — is deterministic: same input → same resolved VFS.

## Invariants

1. Topological sort is deterministic: no arbitrary tie-breaking between independent mods;
   stable ordering by `(mod_id, version)` lexicographic when ordering is ambiguous.
2. A mod's files are applied in load order: mods later in the order override mods earlier
   in the order (higher-priority overrides lower-priority).
3. The base game is always the lowest priority: all mods override the base game's assets.
4. Circular dependency detection is complete: no cycle may exist in the resolved load
   order graph.

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | Two independent mods (no dependencies between them); same set loaded twice | Same load order both times (stable tie-breaking by mod_id lexicographic) |
| EC-002 | Three mods in chain: C depends on B depends on A | Load order: [A, B, C] always |
| EC-003 | Circular dependency: A depends on B, B depends on A | `E-MOD-006` emitted; no mods loaded |
| EC-004 | Two mods override `textures/player.png` | `E-MOD-007` emitted with both mod IDs and the conflicting path; conflict reported but loading continues (conflict is non-fatal; the higher-priority mod's version wins) |
| EC-005 | Mod with no dependencies and no files (empty mod) | Load order includes it (deterministic); no VFS changes; no error |
| EC-006 | Version constraint unsatisfiable: mod A requires mod B >= 2.0.0 but only B 1.5.0 is present | `E-MOD-008` (unsatisfied dependency) emitted; loading rejected |
