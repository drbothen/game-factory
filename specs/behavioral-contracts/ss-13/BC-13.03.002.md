# BC-13.03.002: UGC Content Schema Validation

## Description

When the modding lane is active, the factory generates a `ugc-content-schema` artifact: the
published JSON Schemas defining every moddable data type in the game. These are the same
schemas the factory uses internally to generate and validate base game content — the UGC
ingest gate IS this validator. A mod data file is acceptable if and only if it passes the
schema. Referential completeness (no dangling entity IDs), range/band invariants
(matching the game's design-intent-contract assertions), and schema version matching are
all machine-checkable at ingest time.

## Preconditions

1. The modding lane is active (`modding_enabled: true`) in the validated genre profile.
2. The game's internal content schemas (stat tables, loot tables, recipes, etc.) have been
   generated and version-stamped by the game production pipeline.
3. `modding_config.data_mods` is `true` (data-driven moddability enabled).

## Postconditions

1. A `ugc-content-schema` artifact is generated containing:
   - The published JSON Schema files for each moddable data type (one schema file per
     content type).
   - A schema version consistent with the game's content schema version.
   - A list of moddable types (e.g., `item_stats`, `loot_table`, `recipe`, `room_template`).
2. The UGC ingest gate rejects any mod data file that:
   - Fails JSON Schema validation for its declared content type.
   - Contains a dangling entity reference (references an entity ID not defined in the
     base game or in the same mod's declared additions).
   - Violates declared band/range invariants (e.g., damage > max_damage, negative weight).
3. The schema validator is the same binary used for internal content validation — there is
   no separate UGC-only validator.

## Invariants

1. The UGC content schema is always a projection of the game's internal content schema —
   it never declares types or fields that do not exist in the base game's content model.
2. A mod that passes UGC schema validation is structurally valid but not gameplay-balanced;
   balance quality is human/playtest judgment.
3. The schema version in the `ugc-content-schema` artifact matches the game's content
   schema version at the time of generation (drift detection: if a game update changes the
   internal schema, the UGC schema must be regenerated).

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | Mod data file declares content type `item_stats` but includes fields not in the schema | Validation fails: unknown field rejected in strict mode; `E-MOD-002` emitted |
| EC-002 | Mod data file references an item entity ID that doesn't exist in the base game | Referential completeness check fails: `E-MOD-003` (dangling reference); ingest blocked |
| EC-003 | Mod data sets `damage: 99999` when `max_damage: 1000` is declared in the design-intent contract | Band invariant violation: `E-MOD-004`; ingest blocked |
| EC-004 | Mod data file declares two items with the same `id` field | Uniqueness constraint violation: `E-MOD-005`; ingest blocked |
| EC-005 | Mod data passes schema validation but causes downstream economy inflation | Schema validation does not cover balance; valid by this contract; balance is playtest concern |
