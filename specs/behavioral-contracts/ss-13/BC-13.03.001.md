# BC-13.03.001: Mod-API Contract — Versioned Surface with Semver Stability Enforcement

## Description

When the modding lane is active, the factory generates a `mod-api-contract` declaring the
game's versioned mod-API surface: the set of host functions, types, and capabilities that
a mod may call. The surface is declared as a typed interface (preferring WASM WIT for
machine-typed, semver-able contracts; Luau typed API as secondary; C#/BepInEx patching as
an explicitly-flagged trusted-code lane). The contract enforces semver discipline: breaking
changes to the mod-API surface require a major version bump, and the factory detects
breaking changes by diffing the current surface against the prior release's surface.

## Preconditions

1. The modding lane is active (`modding_enabled: true`) in the validated genre profile.
2. `modding_config.vm` is set to one of: `wasm`, `luau`, `lua`, `csharp_bepinex`.
3. `modding_config.api_version` is a valid SemVer string (e.g., `"1.0.0"`).
4. For `vm: wasm`: a WIT interface file is provided or will be generated from the game's
   internal host-function declarations.
5. For `vm: csharp_bepinex`: the artifact is annotated as `isolation: none` (trusted-code
   model; not sandboxed) and a security advisory is recorded.

## Postconditions

1. A `mod-api-contract` artifact is generated containing:
   - `api_version`: the declared SemVer version.
   - `vm`: the scripting VM choice.
   - `isolation`: `capability_based` (WASM), `language_sandbox` (Luau), `diy_sandbox`
     (plain Lua), or `none` (C#/BepInEx).
   - `surface`: the complete enumeration of callable host functions with their type
     signatures.
   - `breaking_changes`: diff vs prior `api_version` (empty on first release).
2. If `breaking_changes` is non-empty and `api_version` has not incremented the major
   component since the prior version, the pipeline emits `E-MOD-001` (breaking change
   without major version bump).
3. For `vm: wasm`: the WIT interface is schema-validated and version-stamped.
4. For `vm: csharp_bepinex`: the artifact includes a `security_advisory` field noting the
   trusted-code posture and its stability implications (hooks internals → breaks on patches).

## Invariants

1. The mod-API surface is a stable, versioned contract — it is the primary isolation
   boundary between game internals and mod code.
2. Removing or changing the signature of any existing host function is a breaking change
   requiring a major version bump.
3. Adding new host functions is a non-breaking additive change (minor or patch bump).
4. `vm: csharp_bepinex` may never be the factory's recommended default for a new game;
   it is a supported lane but must be explicitly chosen with acknowledged security/stability
   implications.

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | First release (no prior `api_version`): `breaking_changes` check | `breaking_changes` is empty (no prior surface to diff); artifact generated without error |
| EC-002 | Host function renamed across releases without major version bump | `E-MOD-001` emitted; pipeline blocks lane artifact generation until version is bumped |
| EC-003 | WASM WIT declares a host function that calls into game internals not exposed in the VM capability set | WIT schema validation fails: function calls must resolve to declared capabilities |
| EC-004 | Luau sandbox: mod attempts to redefine `require` (protected global) | Sandbox prevents the redefinition at runtime; documented in the contract as an invariant of the Luau sandbox model |
| EC-005 | `api_version` is not a valid SemVer string (e.g., `"v1.0"` instead of `"1.0.0"`) | Schema validation fails (E-GLG-001) |
